# 多智能体研究循环：角色分工不能替代证据

## 从三个脚本到三个职责
多智能体系统的价值不在于给函数起几个角色名字，而在于让不同职责拥有清楚的输入、输出和权限。信号角色提出可检验假设，代码角色把假设转成受限表达式，评价角色使用固定程序计算结果。每一步产物保留编号，后续失败可以追到具体环节，而不是由一个大段自然语言回答包办所有事情。

本课默认运行的是离线流程演练，候选响应由作者预先写好。它会真实计算人工数据上的因子和评价，但没有真实大模型调用。开启第 67 课配置后，才让模型参与假设和表达式生成；最终数值仍由本地确定性评价函数计算。

## 与参考案例的关系
用户提供的 NVIDIA 案例同样分出假设、代码和评价角色，并通过受约束的算子组织研究循环。我们学习这种职责分离，使用更小的 CPU 教学实现，不把原示例环境或模型规模作为学习前提。参考文章中的演示结果也不等于已经发现可靠盈利策略；流程可运行与金融信号有效需要分别判断。

本课只允许动量或反转、2 到 30 的窗口、固定数据和成本。限制范围让你能够逐项核对三种角色是否在讨论同一个问题。扩大算子库之前，应先完成相应公式、参数和时间边界测试。

真实模式只运行一个候选：一次提出假设，一次生成表达式，最后一次对计算报告作文字评论，总调用数不超过三。这样初次接入不会自动扩张成大量付费搜索。文字评论单独标记为未验证，不覆盖本地计算的数值。

## 为什么表达式还要精确匹配
代码角色返回的表达式必须与已经验证的假设一致。若假设为五期动量，模型却输出十期反转，即使表达式本身合法，也不应该悄悄执行。正则和字符串一致性检查把候选之间的对应关系固定下来。执行时仍通过已知公式，不对任意生成 Python 使用 exec。

这个例子支持的语言很小，不应宣传为通用安全沙箱。它只是把当前教学任务限定在能够审阅的范围。真正需要更多功能时，应扩展算子定义和测试，而不是放行所有字符串。

## 评价角色读什么、返回什么
evaluation_agent 只接收已验证的假设，计算因子、目标仓位、简化交易成本和验证均值。它不接收“请让这个策略盈利”的指令，也不让语言模型自行编造绩效。trace 保存每一轮假设、表达式和验证值，不保存最终测试反馈作为下一轮输入。

选定 winner 后才复制 frozen，并计算后段 holdout。代码断言每条搜索 trace 中没有 holdout 字段，帮助防止把最终测试回流到搜索记录。这个结构约束仍不能阻止人看完结果后重开搜索，因此研究日志还要记录何时使用了哪个测试段。

## 一次失败应该停在哪一层
假设字段不合法时，在信号层拒绝；表达式与假设不一致时，在代码层拒绝；数据历史不足或输出非有限时，在评价层拒绝。网络错误也应保留为调用失败，而不是自动用离线响应替换后标成真实成功。

默认客户端没有自动重试。若用户主动重试，应该创建新的尝试记录并计入费用与调用次数。不要把失败调用从日志中删除，因为它们影响真实系统的可靠性和成本。

## 多角色也会共同犯错
三个角色都用同一个模型，并不保证获得三个独立意见。若提示中共享了错误接口或错误标签定义，所有角色可能一致地产生错误结论。职责分工必须配合独立的数值测试、来源核验和时间约束，而不能把“多个 agent 都同意”当作科学验证。

评价模型解释报告时尤其要防止添加不存在的数值。可以要求只引用报告中已存在的字段，并在展示时将原始计算表与文字评论并排。读者能够回到具体数据，才有机会发现解释夸大。

## 参数实验
离线模式下先改变候选窗口列表，记录搜索数量与验证赢家变化。候选变多后，即使数据完全随机，也可能找到更好的验证分数；这正是选择偏差，不是自动发现能力增强的证明。然后固定候选，改变费用，只检查成本敏感性。

真实模式实验由你主动开启，并先使用本地或无敏感内容的短请求。检查模型是否严格返回 JSON、表达式是否匹配、实际调用次数是否符合预期。不能因为离线流程通过就跳过这些接口验收。

## 顺着一条研究轨迹核对角色交接
离线模式中，提出假设的步骤给出允许的窗口，代码步骤返回受限表达式，评价步骤读取程序算出的验证结果并形成摘要。三个角色的名字并不意味着三个独立证据来源：它们共享同一数据和同一协议，任何角色都不能改变测试边界。把职责分开，主要是让每次交接的输入、输出与失败位置更容易检查。

真实模式只让一个候选经过三次请求，目的是限制首次联调规模。第一次结构不合法，就不应继续浪费后续请求；第二次表达式不符合允许格式，也不能因为自然语言解释合理而放行。最终评价文本被标为未经验证的评论，数值结果仍来自程序。模型即使写“表现优异”，也不会改变负收益、费用或冻结配置。

追踪记录应能回答：候选是谁提出的、当时允许看到哪些字段、表达式如何通过检查、验证程序返回哪些数值、最后何时冻结，以及测试何时打开。如果这几项只能从散落的聊天记录猜测，流程还不够可复查。课程把它们放进结构化记录，方便你之后对比离线演练与真实接入的差别。

一个值得故意制造的失败是，让最后的评价角色声称读取了测试指标，但输入中实际上只有验证结果。系统应把这句话看作没有根据的生成内容，而不是自动补给它测试数据。另一个失败是让代码角色请求导入额外包；当前受限协议应直接拒绝，并记录原因。角色协作不能成为扩大权限和数据范围的隐含理由。

后续扩展到多个真实候选时，应先设总调用次数、每轮最多候选数和停止条件，并把解析失败也计入调用预算。否则一次格式错误后的反复修复可能比正式实验消耗更多请求。即便使用本地模型无需按次付费，时间与算力仍是预算，重复读取测试集造成的研究偏差也不会因此消失。

## 练习
1. 三个角色分别负责什么？
2. 为什么真实模式只做一个候选？
3. 评价文字说策略有效而 holdout 很差，应相信谁？
4. 多个角色使用同一错误数据定义会怎样？

## 参考答案
1. 提出假设、生成受限表达式、按固定程序计算评价；最终数值不是模型口头决定。
2. 控制首次接入的调用预算，完整三步最多三次，避免自动扩大成本。
3. 先核对固定计算与数据，文字只是待审阅解释，不能覆盖证据。
4. 它们可能一致犯错，因此还需要独立数值和时间检查。
