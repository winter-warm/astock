# 把自然语言想法写成可检验的研究假设

## 一句建议还缺哪些条件
“尝试短期动量，并用 AI 优化参数”听起来像一个研究方向，却没有明确预测目标、数据字段、决策时点和搜索范围。若每次结果不理想就改变这些条件，实验之间将无法比较。结构化假设卡的作用，是在运行前把这些选择写下来，让人和程序都知道候选究竟是什么。

本课使用冻结的数据类保存假设。它不是为了增加形式感，而是让错误尽早暴露：未知算子、越界窗口或不允许的决策时点，会在计算收益之前被拒绝。这样评估失败不必一直追到最后才发现输入含义不同。

## 假设应包含可观察量
示例包含名称、算子、回看窗口、决策时点、目标跨度和候选编号。名称供人阅读，算子与窗口决定实际计算，决策时点限制信息可用范围，目标跨度固定评价任务，编号用于追踪每次候选。正式项目还可加入数据版本、证券范围、成本和失效条件，但本课先练习最小闭环。

“市场情绪好”如果没有可获得的数据定义，就暂时不是可计算输入。你可以把它保留为需要补资料的假设，而不是让模型凭空生成一列情绪指数。把未知条件明确写成待验证，通常比用任意数字填满表格更有价值。

## 白名单意味着什么
validate 只允许 momentum 和 reversal 两个已定义算子。它不是声称其他指标无效，而是把当前实验限制在能够解释和验证的范围。lookback 限定在 2 到 30 的整数，避免无限搜索，也避免字符串或布尔值被误当成有效参数。

本实验固定一步预测，候选不能在看过结果后把标签改成五步或十步来获得更好分数。若确实要研究不同预测周期，应建立新的实验配置和对应边界，而不是在同一排行榜里混合不同目标。

## 决策时点写进假设
after_completed_bar 表示只有完成的 K 线可以参与计算。它需要与数据构造和执行流程一致；仅在 JSON 里写一句“无未来数据”没有意义。后续表达式执行器与评价函数都必须遵守同一约束，再用反事实测试检查：修改未来数据不能改变过去输出。

同样，目标收益起点应明确。若数据是收盘序列，用当前收盘到下一收盘的收益研究预测关系，需要说明它不是无摩擦成交承诺；真实策略要换成可执行时点或交由 AStock 撮合。这种限制应保留在假设卡说明里，而不是在最终报告中消失。

## 候选编号与去重
同一算子和窗口可能被模型用不同名字重复提出。用名字去重不可靠，应该根据规范化配置形成身份，例如算子、窗口、数据版本与评价设置的组合摘要。重复候选可以记录为重复，但不应把它们当成多份独立发现。

候选编号也用于连接后续代码、测试和结果。假设卡 candidate-001 对应哪份表达式、哪些测试、哪个验证分数，应能一路追溯。若模型修改了窗口，创建新版本，而不是覆盖旧记录后让历史结果失去含义。

## 失效条件要在成功之前写
对动量假设，可以提前写明震荡反复、成本侵蚀或样本覆盖变化等可能失败的情形。它们不是推卸责任，而是帮助设计对照实验。若一个候选只在某一人工趋势段有效，应在结果里说明，而不是把所有失败段删掉。

还应写明拒绝条件，例如缺失过多、历史不足、输出非有限数、未来修改影响过去、评价样本不足。拒绝不一定意味着金融假设永远无效，可能只是当前数据与实现不能支持检验。

## 参数实验
将 lookback 从 5 改成 20，观察假设卡变化，但先不运行收益比较。列出你预期改变的方面：预热长度、更长历史记忆、可能更慢反应。再将窗口设为 0、字符串“5”或布尔值 True，确认校验拒绝它们。类型检查要谨慎，因为 Python 中 bool 是 int 的子类，本例用 type(...) is int 明确排除。

再把 operator 改成 future_return，程序应拒绝。这个名字也许听起来像有用数据，但它在决策时不可知，不能进入允许的候选算子。拒绝名单无法穷尽所有未来信息形式，因此从一开始只允许已审阅算子更容易维护。

## 与模型协作的方式
向真实模型请求假设时，提供当前允许字段和算子文档，让它只提出范围内候选。返回后仍调用同一个 validate，不因为来自更强模型而跳过检查。若模型提出范围外想法，先作为人工研究建议保存，经过定义和实现审核后再扩展算子库。

这种流程保留创造性，同时把执行边界固定下来。你可以让模型写为什么想尝试，但评估是否成功仍交给固定数据和计算程序。

## 用一个候选假设检查每个字段有没有落地
以“过去五期上涨后，下一期仍有正收益倾向”为例，操作符选择动量，窗口设为五，决策时点是完整行情柱结束后，预测期是一。这里的五与一承担不同职责：前者限制可用历史，后者定义标签结束时间。若模型把预测期偷偷改成五，却继续沿用一周期隔离间隔，代码仍可能运行，训练标签却会跨进验证区间。因此本课先固定预测期，减少候选空间中不受检查的自由度。

窗口必须是整数，且处于明确范围。布尔值在某些语言或库中可以被当成整数使用，尤其在 Python 中真假值与整数类型关系特殊；若只检查是否属于整数而不排除布尔，真可能变成窗口一。代码用精确类型检查加范围约束，拒绝这种虽然能被程序解释、却不符合研究意图的输入。

未知字段也需要处理。如果模型额外加入“保证收益”或“自动扩大仓位”，不能悄悄忽略后继续把整个响应称为已验证。严格模式应拒绝不符合协议的字段，让错误在入口被看见。对真正需要增加的字段，先修改协议、验证器、执行器与测试，再让模型使用新版本，避免自然语言悄悄拓宽系统能力。

你可以制作一个表，分别填入合法窗口五、过大窗口九十九、字符串窗口五、布尔窗口真，以及未知操作符。预期只有第一项通过。然后再做语义检查：即使第一项通过，它也只是一条可执行、可评价的假设，并未获得有效性证明。结构验证与统计评估之间应保留清楚的状态，不要让“通过”一个词同时表示所有环节成功。

候选冻结后应能稳定序列化，同一组字段使用固定顺序与数值表示生成摘要。这样后续报告可以确认究竟评价了哪条假设，而不是只保存“动量策略”这样的泛名。若窗口从五改为十，摘要应改变，并形成新的候选记录。把修改前后的结果并列保留，才能看见调参次数；覆盖旧文件会让研究历史看起来比实际更简单。

这种窄协议牺牲了一部分自由表达，但很适合初学者理解自动化的边界。等你能够证明新增操作符的公式、时间依赖和异常处理，再逐步扩大协议。扩大候选数量前先提高验证能力，比一次允许任意脚本更容易得到可复查的学习成果。
